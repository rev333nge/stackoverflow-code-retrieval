STACKOVERFLOW CODE SEARCH — RESULTS
===================================

PHASE PROGRESSION  (variant A, TEST set, 19,065 queries)
    phase                        NDCG@10   MRR@10   Recall@100
    1  BM25 baseline              0.6893   0.7190     0.9309
    2  code-aware tokenizer       0.7148   0.7437     0.9448    (+3.7% NDCG)
    3  dense retrieval (bge)      0.7989   0.8288     0.9788    (+11.8% NDCG)
    5  hybrid (RRF, k=5)          0.8160   0.8436     0.9871    (+2.1% NDCG)

    Each phase must beat the last on the held-out test set. (Phase 4 is
    analysis, not a new model — no row.)


WHAT THE METRICS MEAN
    NDCG@10     ranking quality in the top 10 (1.0 = perfect)
    MRR@10      how soon the first useful answer appears (avg 1/rank)
    Recall@100  % of relevant answers found anywhere in the top 100


KEY READ
    BM25: recall high (0.94) but NDCG lower (0.71) -> found, not well ranked.
    Dense fixed much of that: recall 0.98 (misses halved) AND better ranking,
    because it matches meaning (flip = reverse, typos, paraphrases) not strings.
        -> remaining ranking headroom      -> Phase 6 (learning-to-rank)
        -> BM25 still wins on exact terms
           (pd.merge, error strings)        -> Phase 4 diagnoses, Phase 5 fuses


PHASE 1 — BM25 baseline
    Variant A (title + answer) beat B (title + question + answer) on val, so
    the document is title + answer; the question body added length and noise.
        variant A   val  NDCG@10 0.6865    test 0.6893   (stable, no overfit)


PHASE 2 — code-aware tokenizer
    Keep code identifiers intact instead of shredding them:
        np.array  -> np, array, np.array       read_csv  -> read, csv, read_csv
        DataFrame -> data, frame, dataframe     pure numbers dropped
    Parts help recall; the rare compound tokens (high IDF) sharpen ranking.
        val  0.7104 / 0.7412 / 0.9448      test  0.7148 / 0.7437 / 0.9448

    Stemming — TRIED, DROPPED (negative result)
        English stemming (arrays -> array, merging -> merg) HURT every metric
        on val: NDCG@10 0.7104 -> 0.6400. Stemming lowers the IDF of exact
        technical terms — the signal code search leans on — so precision and
        even recall fell. Kept the unstemmed tokenizer.


PHASE 3 — dense retrieval (embeddings + FAISS)
    Encode each document into a 768-d meaning-vector with bge-base-en-v1.5
    (fp16 on GPU), index with FAISS flat (cosine). Search embeds the query and
    returns nearest vectors. Matches meaning, not keywords, so synonyms / typos /
    paraphrases that BM25 scored 0 now hit.
        val   0.7929 / 0.8228 / 0.9798     test  0.7989 / 0.8288 / 0.9788
    Biggest single-phase jump so far (+11.8% NDCG vs Phase 2). Recall miss rate
    5.5% -> 2.0%.


PHASE 5 — hybrid (RRF)
    Reciprocal Rank Fusion merges the BM25 and dense ranked lists using rank
    position only, not raw scores — BM25 scores and cosine similarities live
    on different scales, so averaging them directly wouldn't mean anything.
    For each candidate doc: score = sum of 1/(k+rank) over whichever list(s)
    it appears in; sort by that score, keep the top 100. k controls how much
    a rank difference near the top gets trusted — small k makes rank 1 worth
    a lot more than rank 2, large k treats nearby ranks as roughly tied.

    k = 60 is the standard default from the original 2009 RRF paper, but
    that's popular because RRF tends not to be very sensitive to k, not
    because 60 is right for this data specifically. Swept it on val instead
    of assuming it (val, 15,923 queries):

        k     NDCG@10   MRR@10   Recall@100
        1      0.8107   0.8402     0.9876
        2      0.8119   0.8416     0.9876
        5      0.8123   0.8414     0.9876
        10     0.8119   0.8401     0.9876
        20     0.8089   0.8362     0.9876
        40     0.8039   0.8328     0.9876
        60     0.8014   0.8312     0.9876
        100    0.7998   0.8300     0.9876
        200    0.7991   0.8293     0.9876

    NDCG@10 peaks at k=5, not at the literature default — the curve rises
    from k=1 to k=5 then falls off steadily through k=200, a real peak rather
    than the edge of the grid, so it's not just noise from trying several
    values on val. MRR@10 peaks at k=2, but k=5 is within 0.0002 of it —
    close enough to call it the same. Picked k=5.

    Recall@100 is flat across every k. Makes sense once you separate what k
    actually controls: it reorders candidates within the merged pool, it
    doesn't change who's in the pool. A relevant doc that either method
    retrieves at all tends to come back at a decent rank already (that's
    where BM25/dense's own ~93-98% recall@100 came from), so its combined
    score clears the top-100 cutoff no matter what k is. k moves it from,
    say, rank 40 to rank 8 inside that cutoff — which NDCG@10 and MRR@10
    notice, since they only look at the top 10, and recall doesn't.

        val (k=5)    0.8123 / 0.8414 / 0.9876
        test (k=5)   0.8160 / 0.8436 / 0.9871

    Beats dense alone on both splits, every metric. Confirms the Phase 4
    read: BM25 and dense are complementary, and fusing them recovers some of
    that oracle headroom (val oracle 0.8563 vs val dense 0.7929, gap 0.0634;
    hybrid closes it to 0.0440 — about 30% of the gap gone).
